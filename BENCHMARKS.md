# Benchmarks: zoptia0regex (Zig) vs Go `regexp`

A like-for-like performance comparison between this Zig port and the Go
standard-library `regexp` it is modelled on. The two engines produce
identical match results (enforced by the differential suite, see
[README](README.md#trust--validation)); this measures how fast they get
there.

Every number on this page is generated: `tools/bench.sh` runs both
harnesses and `tools/cmd/benchtable` rewrites the blocks between the
`BEGIN GENERATED` / `END GENERATED` markers (here and in the README
headline). Do not edit those blocks by hand; regenerate them.

## Methodology

- **Identical inputs.** Both harnesses run the same patterns over the same
  bytes: a 256 KB deterministic mixed-text corpus (`bench/data/bench_corpus.txt`)
  for scans, and short literal strings for the anchored "validation" cases.
  The cases live in `bench/data/bench.jsonl`, generated by
  `tools/cmd/genbench`.
- **Same calibration.** Each operation runs in a loop whose iteration count
  doubles until a batch exceeds 250 ms; five batches are then timed at that
  count and the fastest is reported (`ns/op = fastest_batch_ns / iters`), so
  a burst of background load cannot inflate a row. Compile time is measured
  the same way with a 100 ms target. The logic is identical in
  `bench/bench.zig` and `tools/cmd/benchgo`.
- **Same answers.** Each harness also records the value of one single run
  of every operation (a sum over the match offsets), and `benchtable`
  refuses to produce a table if the Zig and Go values differ.
- **Optimized builds.** Zig is `-OReleaseFast`; the Go harness is a normal
  `go build` binary of the reference toolchain (go1.27.1), so no build time
  is measured.
- **Allocation.** The Zig harness resets an arena (`retain_capacity`) per
  iteration, so scratch allocation is a cheap bump, the analogue of Go's
  per-`Regexp` machine pool. The library also has a first-class
  zero-allocation path (`matchScratch`); see
  [the Scratch API](#allocation-free-matching-the-scratch-api) below.
- **Engine column.** The Zig harness reports which path the port's dispatch
  takes for each case: `literal` (the complete-literal fast path, no engine),
  `one-pass`, `bitstate` or `Pike VM`, with `+prefix` (literal-prefix scan)
  or `+first-bytes` (SIMD first-byte prefilter) when an accelerator skips
  ahead. Go does not expose its choice; it uses the same dispatch minus the
  port's additions (the literal fast path and the first-byte prefilter).

## Where the differences come from

- **Pike VM scans.** No GC, an ASCII fast path in the rune decoder, an ASCII
  membership bitmap per `rune` instruction (a side table, so `Inst` stays 32
  bytes), and a find-all loop that, like Go 1.27's `matches` iterator,
  reuses one engine scratch and records only the whole-match slots when
  that is all the caller needs.
- **SIMD first-byte prefilter (no Go counterpart).** When a pattern has no
  literal prefix but can only start with one of at most 16 ASCII bytes (a
  case-insensitive literal, `\d`, a small class, the first bytes of an
  alternation), the unanchored engines skip ahead with a portable
  `@Vector` sweep where Go steps its NFA at every position. The
  `+first-bytes` rows show its effect.
- **Literal prefixes.** The prefix scan anchors on the prefix's rarest byte
  and switches to Rabin-Karp once false starts cost more than a few units
  per haystack byte, so it stays O(n + m) (`src/search.zig`).
- **Complete literals skip the engines.** When the regexp is exactly a
  literal (complete prefix, no captures, no start condition), every search
  that needs at most the whole-match location is a substring search, with
  no engine setup and no allocation (the `literal` rows).
- **One-pass.** Anchored patterns that qualify run Go's one-pass engine,
  including Go's literal-prefix skip.
- **Alternation factoring.** The parser runs Go's `factor` pass, so a
  keyword list compiles to Go's program instruction for instruction instead
  of one Pike VM thread per branch.
- **Compilation.** The port does slightly different up-front work (the
  one-pass copy, first-byte analysis, the ASCII bitmaps) and pays no GC.
- **Small-input bitstate.** On the nested-quantifier case (`redos_linear`,
  2 KB input) both sides run the bitstate backtracker; both are linear-time
  and finish in microseconds.

## Allocation-free matching: the `Scratch` API

Go pools its `*machine` per `Regexp` in a `sync.Pool`, so a hot match loop
allocates nothing in steady state. The port offers the same through a
caller-owned `Scratch`: allocate one (`Scratch.init(gpa)`), then call
`re.matchScratch(&scratch, input)` / `re.findSubmatchIndexScratch(&scratch, …)`
in a loop. Once warm, every call does zero heap allocation: the sparse-set
queues, thread pool and bitstate buffers are reused, growing to a
high-water mark and never shrinking. The allocating API (`match`, `find`,
…) wraps the same code path with a temporary scratch that is set up only
when an engine actually runs and takes its first 2 KB from the stack, so a
search over a short input usually never reaches the allocator.

## Reproduce

```sh
tools/bench.sh                       # run everything, rewrite the generated blocks
BENCH_OUT=/some/dir tools/bench.sh   # same, and keep the raw TSVs

# or piece by piece (each prints TSV on stdout):
zig build bench
zig build bench-scratch
( cd tools && go build -o /tmp/benchgo ./cmd/benchgo ) && /tmp/benchgo -data bench/data
( cd tools && go build -o /tmp/benchscratchgo ./cmd/benchscratchgo ) && /tmp/benchscratchgo -data bench/data
```

`tools/regen.sh` regenerates the workloads in `bench/data/` along with the
test corpora.
