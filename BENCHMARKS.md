# Benchmarks: zoptia0regex (Zig) vs Go `regexp`

A like-for-like performance comparison between this Zig port and the Go
standard-library `regexp` it is modelled on. The two engines produce
**identical match results** (verified by ~48k differential cases); this measures
how fast they get there.

**Headline:** across 20 representative workloads the Zig port is, on average,
**~53% faster** (geomean Zig/Go = **0.47×**; **0.54×** if the
literal-hit row, now a bare substring search, is left out) and **~1.4× faster
at compiling**. It ships all three of Go's engines (Pike VM, bitstate
backtracker, one-pass) plus a SIMD first-byte prefilter and a complete-literal
fast path Go lacks; Go is ahead on just one workload — a small-input bitstate
case at 1.13×, both sides in single-digit microseconds.

## Methodology

- **Identical inputs.** Both harnesses run the *same* patterns over the *same*
  bytes: a 256 KB deterministic mixed-text corpus (`src/bench_corpus.txt`) for
  scans, and short literal strings for the anchored "validation" cases. Cases
  live in `src/bench.jsonl`, generated by `tools/genbench.go`.
- **Same calibration.** Each operation runs in a loop whose iteration count
  doubles until a batch exceeds 250 ms; `ns/op = batch_ns / iters`. Compile time
  is measured the same way. Identical logic in `tools/benchgo.go` and
  `src/bench.zig`.
- **Optimized builds.** Zig is `-OReleaseFast`; Go is the standard `go run`
  build. A result checksum is accumulated and `doNotOptimizeAway`'d to prevent
  dead-code elimination.
- **Allocation.** The Zig harness resets an arena (`retain_capacity`) per
  iteration so scratch allocation is a cheap bump — the fair analogue of Go's
  per-call machine `sync.Pool`. The library also exposes a first-class
  zero-allocation path (`matchScratch`); see
  [Allocation-free matching](#allocation-free-matching-the-scratch-api) below.
- **Same engine selection.** The port mirrors Go's dispatch exactly: the
  **one-pass** engine for qualifying anchored regexps, the **bitstate**
  backtracker for small programs/inputs, and the **Pike VM** otherwise; all
  with literal-prefix acceleration (anchored on the prefix's *rarest* byte,
  rust-memmem-style, with a Rabin-Karp fallback like Go's `bytes.Index`). On
  top of that the port adds a **first-byte prefilter** Go does not have: when
  no literal prefix exists but every match starts with one of ≤ 16 ASCII
  bytes (a case-insensitive literal, `\d`, a small class), the unanchored
  engines skip ahead with a portable SIMD sweep (`@Vector` → NEON on aarch64,
  SSE2 on baseline x86_64). Results stay identical — the differential suite
  proves it.

> Checksums differ between the harnesses only because calibration runs a
> different iteration count on each; the per-call results are identical (proven
> by the differential suite).

## Analysis

**General NFA engine (Pike VM): faster across the board.** On the
throughput-bound findall workloads the port is ~20–35% faster (`charclass_word`
0.66×, `perl_word` 0.64×, `unicode_letters` 0.64×, `anchored_multiline` 0.75×,
`nested_groups` 0.74×, `email` 0.82×). No GC, `-OReleaseFast`, an ASCII fast
path in the rune decoder, and — since the Go 1.27 sync — a `findAll` loop
that, like Go 1.27's `matches` iterator, reuses one engine scratch and (for
the index/text variants) records only the two whole-match slots instead of
every capture. Before that, each match in a `findAll` re-allocated the VM's
queues and thread pool (~14 allocations per match on `\w+`), which is why
these rows used to sit at 0.9–1.0×.

**The SIMD first-byte prefilter turns former losses into the biggest wins.**
When a pattern has no literal prefix but can only *start* with one of ≤ 16
ASCII bytes, the port skips ahead with a portable SIMD sweep where Go steps
its NFA at every position. `date` and `digits` (`\d`-led, a 10-byte set) drop
to **0.18×** and **0.17×** — 5.5–6× faster than Go; `caseins_literal` —
`(?i)performance` scanned unanchored over 256 KB, formerly the port's one loss
at 1.29× — runs at **0.22×** (4.5× faster than Go), its scan living in a NEON
`p`/`P` sweep instead of the VM. `alternation` (first bytes of each branch)
lands at **0.33×**, `dotstar_greedy` at **0.73×**. Go has no equivalent
accelerator.

**Anchored "validation" patterns (one-pass): ~2× faster than Go.** Anchored
regexps (`\A…\z`) — the bread-and-butter of input validation — qualify for the
one-pass engine: a single deterministic pass with no thread set. With the
literal-prefix skip (`onePassPrefix`) and the ASCII decode fast path, the port
now wins every such case at **0.47–0.78×**.

**Compilation is ~1.4× faster** (geomean 0.72×) — Go does more up-front work
and pays GC overhead; the port spends a little extra on its one-pass deep
copy, first-byte analysis and the linear `\p{…}` name lookup over Go's full
category/script set, and still compiles comfortably faster.

**Benchmark-driven gaps, all closed by porting the matching Go machinery (or
adding our own):**

| gap | before | after | how |
|-----|-------:|------:|-----|
| literal search (`literal_miss`) | 310× | **0.98×** | rarest-byte-anchored prefix accel |
| nested quantifier (`redos_linear`) | 3.89× | **1.09×** | bitstate backtracker (small inputs) |
| anchored case-insensitive | 1.27× | **0.62×** | one-pass engine + prefix skip |
| unanchored case-insensitive | 1.29× | **0.25×** | SIMD first-byte prefilter (no Go counterpart) |

**Complete literals skip the engines.** When the regexp is exactly a literal
(`prefix_complete`, no captures, no assertions, no case folding), `match` /
`findIndex` answer with the prefix search alone — no machine setup, no
allocation. `literal_hit` drops from ~200 ns (a Pike VM start-up plus one
memchr) to **5 ns**; `literal_miss` is unchanged, since it was already one
substring search over 256 KB.

**The one remaining non-win is `redos_linear` (1.13×)** — the bitstate engine
on a 2 KB input, where Go's small-input constant is slightly lower. Both
implementations are linear-time (no exponential blowup) and finish in
single-digit microseconds.

## Allocation-free matching: the `Scratch` API

Go pools its `*machine` per `Regexp` via `sync.Pool`, so a hot match loop
allocates nothing in steady state. This port now offers the same through a
caller-owned **`Scratch`**: allocate one (`Scratch.init(gpa)`), then call
`re.matchScratch(&scratch, input)` / `re.findSubmatchIndexScratch(&scratch, …)`
in a loop. After it warms up, **every call does zero heap allocation** — the
sparse-set queues, thread pool and bitstate buffers are all reused, growing to a
high-water mark and never shrinking. The existing `match` / `find` / … API is
unchanged; it wraps the same code path with a temporary scratch.

The win shows up on short-input hot loops, where the old per-call `Machine`
allocation dominated. Same patterns, same 200 ms calibration, Apple M4,
`-OReleaseFast` vs go1.26.4 (measured before the Go 1.27 sync; the engine paths are unchanged):

| pattern | engine | Go `MatchString` | Zig `match` (alloc) | Zig `matchScratch` | scratch vs Go |
|---------|--------|-----------------:|--------------------:|-------------------:|--------------:|
| `needle` (literal) | bitstate+prefix | 46 | 53 | **22** | **0.48×** |
| `\A\d+\z` (anchored) | one-pass | 88 | 39 | **35** | **0.40×** |
| `[0-9]+` | bitstate+first-bytes | 88 | 68 | **42** | **0.48×** |
| `(foo\|bar\|baz)+` | bitstate+first-bytes | 88 | 68 | **42** | **0.48×** |
| `[a-z]+@[a-z]+\.[a-z]+` | Pike VM | 376 | 362 | **294** | **0.78×** |

Reading the table: **before** the `Scratch` API, per-call allocation made the
port 1.3–1.6× *slower* than Go's pooled machine on the bitstate / Pike-VM
patterns. With the allocation gap closed, the numbers reduce to pure engine
throughput — and after the SIMD first-byte prefilter and the ASCII decode
fast path, the port now wins **every** row (0.40–0.78×), including the
unanchored Pike-VM scan that used to be Go's remaining edge.

> These are 20–50 byte inputs, where fixed per-op overhead weighs most; on the
> 256 KB corpus above the same engines land at a **0.64×** geomean. The two
> views are consistent — different input scales.

## Reproduce

```sh
tools/regen.sh                              # (re)generate the corpus + cases
zig build bench                             # Zig results (ReleaseFast) -> stderr TSV
( cd tools && go run benchgo.go )           # Go results -> stdout TSV

zig build bench-scratch                     # Zig Scratch-reuse benchmark
( cd tools && go run bench_scratch_go.go )  # Go counterpart
```
